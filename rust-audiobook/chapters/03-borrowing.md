# 第三章 借用：不转移所有权的访问

上一章我们学了一条铁律：每个值只有一个 owner，把值传给函数，所有权就跟着走了，原来的变量就废了。这条规则很安全，但也很不方便。想象一下，你写了一个函数，只是想看一眼一个 String 的长度，结果调用完之后，原来那个 String 就不能用了。每次都要靠返回值把所有权还回来，代码会变得非常啰嗦。

Rust 的解决方案叫做借用。借用的意思是：我不拿走你的东西，我只是借来看看，用完了还给你。这一章我们讲三件事：不可变引用怎么用，可变引用怎么用，以及 borrow checker 为什么不让你同时用两种引用。

## 不可变引用：借来看看

最常见的场景是：你有一个值，想传给一个函数读取，但不想放弃所有权。这时候你可以传一个引用。

我们来看一个例子。定义一个函数 calculate_length，参数不是 String，而是对 String 的引用，写作 &String。调用的时候，你在变量前面加一个 & 符号，表示"我借给你看看"。

```rust
fn calculate_length(s: &String) -> usize {
    s.len()
}

fn main() {
    let s1 = String::from("hello");
    let len = calculate_length(&s1);
    println!("'{}' 的长度是 {}", s1, len);
}
```

注意，调用 calculate_length 之后，s1 依然有效。所有权没有转移，我们只是把 s1 借了出去。函数结束后，引用消失，但 s1 还是 s1 的 owner。

这里有一个重要的限制：不可变引用只能读，不能改。如果你在 calculate_length 里试图修改 s，编译器会拒绝。这就像你借了朋友的书，可以翻着看，但不能在上面写字。

而且，不可变引用可以同时存在多个。你可以把同一个 String 借给三个函数同时读，没有任何问题。多个读者不会互相干扰，所以编译器允许。

```rust
fn main() {
    let s = String::from("hello");
    let r1 = &s;
    let r2 = &s;
    let r3 = &s;
    println!("{}, {}, {}", r1, r2, r3);
}
```

所以记住：不可变引用的规则是——可以有任意多个，但只能读，不能写。

## 可变引用：借来改改

有时候你确实需要修改借来的值。Rust 提供了可变引用，写作 &mut。要使用可变引用，原来的变量本身必须是 mut 的，而且函数参数也要声明为 &mut String。

```rust
fn add_world(s: &mut String) {
    s.push_str(", world");
}

fn main() {
    let mut s = String::from("hello");
    add_world(&mut s);
    println!("{}", s);
}
```

这段代码可以编译通过。add_world 通过可变引用修改了 s 的内容，调用结束后 s 变成了 "hello, world"。所有权始终在 main 里，add_world 只是借来改了一下。

但是，可变引用有一条严格的限制：同一时刻，对同一个值只能存在一个可变引用。如果你试图同时创建两个可变引用，编译器会报错。

```rust
fn main() {
    let mut s = String::from("hello");
    let r1 = &mut s;
    let r2 = &mut s; // 编译错误：cannot borrow `s` as mutable more than once
    println!("{}, {}", r1, r2);
}
```

为什么要有这条限制？因为如果两个可变引用同时存在，就意味着两段代码可以同时修改同一块数据。在单线程里，这会导致逻辑错误；在多线程里，这就是数据竞争。Rust 在编译期直接把这条路堵死了。

所以记住：可变引用的规则是——同一时刻只能有一个，但这一个可以读也可以写。

## 不可变和可变不能共存

接下来是最容易让初学者困惑的一条规则：不可变引用和可变引用不能同时存在。

我们来看一个例子。先创建一个 String，拿到两个不可变引用 r1 和 r2，然后试图再拿一个可变引用 r3。

```rust
fn main() {
    let mut s = String::from("hello");
    let r1 = &s;
    let r2 = &s;
    let r3 = &mut s; // 编译错误
    println!("{}, {}, {}", r1, r2, r3);
}
```

编译器会说：cannot borrow s as mutable because it is also borrowed as immutable。

这条规则背后的道理很直观：如果有人正在读一个值，而你突然把值改了，读的人拿到的数据就不一致了。Rust 把这种冲突消灭在编译期。

不过，这里有一个细节值得注意。Rust 的 borrow checker 并不是简单地看"同一个作用域里有没有同时声明两种引用"。编译器实际上追踪的是引用的使用范围。如果不可变引用在某一行之后就再也没被用过，那从那一行开始，你就可以创建可变引用了。这个特性叫做 non-lexical lifetime，简称 NLL。

```rust
fn main() {
    let mut s = String::from("hello");
    let r1 = &s;
    let r2 = &s;
    println!("{}, {}", r1, r2);
    // r1 和 r2 在这之后再也没被用过
    let r3 = &mut s; // 没问题
    println!("{}", r3);
}
```

这段代码可以编译通过，因为 r1 和 r2 的最后一次使用在 println 那一行，之后编译器认为不可变引用已经结束了，所以允许创建可变引用 r3。

换句话说，borrow checker 关心的是引用实际被使用的范围，而不是变量声明的作用域。这让规则严格的同时又不会过度限制你。

## 悬垂引用：编译器的底线

还有一种情况编译器绝对不会放过，那就是悬垂引用。悬垂引用的意思是：一个引用指向的值已经被释放了，但引用还在被使用。在 C 语言里，这是经典的 use-after-free bug。在 Rust 里，这是编译错误。

我们来看一个例子。写一个函数 dangle，在函数内部创建一个 String，然后试图返回对这个 String 的引用。

```rust
fn dangle() -> &String {
    let s = String::from("hello");
    &s
}
```

编译器会拒绝这段代码。原因很明确：s 是在 dangle 函数内部创建的，当 dangle 执行结束，s 离开作用域，String 的内存被释放。如果编译器允许你返回 &s，那调用者拿到的就是一个指向已释放内存的引用——一个悬垂指针。

Rust 的做法是：如果编译器发现引用可能比引用指向的值活得更久，直接编译失败。正确的写法是返回 String 本身，把所有权交给调用者，而不是返回引用。

```rust
fn no_dangle() -> String {
    let s = String::from("hello");
    s
}
```

这就是 Rust 的核心承诺之一：只要你的代码编译通过，就不会出现悬垂引用。编译器替你检查了所有引用的有效性。

## 回顾

我们来回顾这一章的要点。

第一，不可变引用 &T 允许你读取一个值而不转移所有权。不可变引用可以同时存在多个。

第二，可变引用 &mut T 允许你修改一个值而不转移所有权。但同一时刻只能有一个可变引用。

第三，不可变引用和可变引用不能同时存在，这是 Rust 在编译期防止数据竞争的关键手段。borrow checker 追踪的是引用实际被使用的范围，而不是变量的词法作用域。

第四，引用不能比引用指向的值活得更久。试图创建悬垂引用会导致编译错误，这让 use-after-free 这类 bug 在 Rust 中彻底消失。

下一章我们会看到，当编译器需要在函数签名中表达"这个引用能活多久"的时候，就需要用到一个新概念——生命周期。
