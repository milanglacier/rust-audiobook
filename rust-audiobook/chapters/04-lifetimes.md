# 第四章 生命周期：编译器的记忆

假设你写了一个函数，接收两个字符串切片，返回其中比较长的那个。逻辑很简单，你很快就写完了。然后编译器报错了，说它不知道返回的引用能活多久。你明明只是返回了一个参数，为什么编译器会困惑？这就是生命周期要解决的问题。

这一章讲三件事：生命周期到底是什么，编译器什么时候能自己推断，以及你什么时候必须手动标注。

## 生命周期是什么

我们先回到上一章的核心规则：引用不能比它指向的值活得更久。borrow checker 要确保这一点，但它需要一种方式来追踪每个引用的有效范围。这种追踪机制，就叫生命周期。

每个引用都有一个生命周期。生命周期就是这个引用从创建到最后一次使用之间的那段作用域。注意，不是到变量被销毁，而是到最后一次使用。Rust 的 borrow checker 足够聪明，它追踪的是实际使用范围，不是词法作用域。

来看一个例子。我们创建一个 String，然后创建一个指向这个 String 的引用，接着在引用还有效的时候使用引用。这是合法的，因为引用的生命周期完全在值的生命周期之内。

```rust
let s = String::from("hello");
let r = &s;
println!("{r}");
```

但如果你尝试在值被释放之后使用引用，编译器就会拒绝。我们来看一个经典的悬垂引用场景：在一个内部作用域里创建 String，把引用传到外面，然后 String 被释放了，引用就悬空了。

```rust
let r;
{
    let s = String::from("hello");
    r = &s;
} // s 在这里被释放
// println!("{r}"); // error: `s` does not live long enough
```

编译器会说 s does not live long enough。换句话说，s 的生命周期比 r 的生命周期短，引用在值死后还想被使用，borrow checker 不允许。

在大多数代码里，你不需要想这些。编译器自己就能看出每个引用活多久，自动检查。但有一类情况，编译器看不透——当引用跨越函数边界的时候。

## 函数签名中的生命周期标注

回到开头那个问题。你写了一个函数，接收两个字符串切片，返回较长的那一个。

```rust
// 编译不过
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}
```

编译器报错了。错误信息说：missing lifetime specifier，也就是缺少生命周期标注。

为什么？因为编译器不知道返回的引用到底跟 x 的生命周期走，还是跟 y 的生命周期走。这取决于运行时 x 和 y 哪个更长，编译器在编译期没法确定。所以它要求你用生命周期参数来告诉它：返回值的引用和输入参数的引用之间是什么关系。

修复的方式是加一个生命周期参数。我们用 'a 来标注，告诉编译器：返回值的引用，至少和 x、y 中较短的那个生命周期一样长。

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

这里的关键是：'a 不是说 x 和 y 的生命周期相同。'a 表示的是 x 和 y 的生命周期的交集，也就是两者重叠的那部分。返回值的引用在这个交集范围内是安全的。

这个标注不会改变任何值的实际生命周期。生命周期标注只是给编译器的提示，让 borrow checker 能够验证调用者传进来的引用确实满足约束。

来看一个调用这个函数的例子。如果两个字符串的生命周期不同，结果的生命周期就是较短的那个。

```rust
let s1 = String::from("long string");
let result;
{
    let s2 = String::from("hi");
    result = longest(s1.as_str(), s2.as_str());
    println!("{result}"); // OK：在 s2 还活着的时候使用
}
// println!("{result}"); // error：s2 已经死了，result 不能用了
```

borrow checker 看到 result 的生命周期被绑定到 s1 和 s2 中较短的那个，也就是 s2。s2 在内部作用域结束时被释放，所以 result 在那之后就不能用了。这就是生命周期标注的作用：它不改变行为，它让编译器能够检查行为。

## 生命周期省略规则

你可能会想：我之前写了那么多接收引用的函数，从来没标注过生命周期，也编译过了。这不矛盾吗？

不矛盾。因为 Rust 有一套生命周期省略规则。编译器在三种常见模式下能自动推断生命周期，不需要你手写。

第一条规则：每个引用参数都有自己独立的生命周期。如果函数有一个引用参数，它就有一个生命周期 'a；有两个引用参数，就有 'a 和 'b，以此类推。

第二条规则：如果刚好只有一个引用参数，那么返回值的生命周期就等于这个参数的生命周期。这很直觉——只有一个来源，返回的引用一定来自这个来源。

第三条规则：如果参数里有 self 的引用，也就是方法调用，那么返回值的生命周期等于 self 的生命周期。这也很合理——方法通常返回的是自身某个部分的引用。

来看一个例子。这个函数只有一个引用参数，根据第二条规则，返回值的生命周期自动等于这个参数的生命周期，所以不需要标注。

```rust
fn first_word(s: &str) -> &str {
    // ...
}
// 编译器自动推断为：
// fn first_word<'a>(s: &'a str) -> &'a str
```

但 longest 函数有两个引用参数，第二条规则不适用，第三条也不适用，因为 longest 不是方法。编译器推断不了，所以你必须自己标注。

换句话说，省略规则覆盖了绝大多数日常场景。只有当编译器用完三条规则还是不确定的时候，它才会要求你手动标注。

## Struct 中的生命周期

函数不是唯一需要生命周期标注的地方。如果一个 struct 持有引用，你也必须标注。

原因很直接：struct 可能活很长时间，如果 struct 里的引用指向的值先被释放了，struct 就持有了一个悬垂引用。编译器需要生命周期参数来防止这种情况。

我们来定义一个 struct，它持有一个字符串切片。这个 struct 叫 ImportantExcerpt，用来保存一段文本的引用。

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}
```

这个标注告诉编译器：ImportantExcerpt 实例的生命周期不能超过 part 指向的字符串的生命周期。如果字符串先被释放，任何持有这个引用的 ImportantExcerpt 实例都不能继续存在。

```rust
let novel = String::from("Call me Ishmael. Some years ago...");
let first_sentence = novel.split('.').next().unwrap();
let excerpt = ImportantExcerpt { part: first_sentence };
println!("{}", excerpt.part);
```

这段代码是合法的，因为 excerpt 的生命周期在 novel 的生命周期之内。如果你尝试让 excerpt 活得比 novel 更久，编译器会拒绝。

一个实用的建议：如果你发现自己在 struct 里加了很多生命周期参数，代码变得很复杂，可以考虑让 struct 拥有数据而不是借用数据。用 String 代替 &str，用 Vec 代替 &[T]。多一次 clone 的开销，换来简单得多的类型签名，在很多场景下是值得的。

## 'static 生命周期

最后说一个特殊的生命周期：'static。'static 表示这个引用可以活到整个程序结束。

最常见的 'static 引用是字符串字面量。所有的字符串字面量都是 'static 的，因为字符串字面量的内容被编译进了程序的二进制文件里，程序运行期间一直存在。

```rust
let s: &'static str = "hello, world";
```

你在错误信息里经常会看到编译器建议你加 'static。但要小心，这个建议大多数时候是错的。编译器建议 'static 是因为 'static 一定能满足约束，但真正的修复通常是调整你的代码结构，而不是让所有东西都活到程序结束。

换句话说，当你看到编译器说 consider using the 'static lifetime 的时候，先想一想：这个值真的需要活到程序结束吗？大多数时候答案是否定的。

## 回顾

我们来总结这一章的三个要点。

第一，生命周期是编译器追踪引用有效范围的机制。每个引用都有一个生命周期，borrow checker 用生命周期来确保引用不会比它指向的值活得更久。

第二，大多数时候你不需要手写生命周期。编译器的省略规则覆盖了绝大多数场景。只有当函数返回引用且有多个引用参数，或者 struct 持有引用时，你才需要标注。

第三，'static 意味着活到程序结束。字符串字面量是 'static 的，但不要轻易听从编译器"加 'static"的建议。

到这里，所有权三部曲就讲完了：所有权、借用、生命周期。这三个概念是理解 Rust 的基石。从下一章开始，我们转向 Rust 的数据建模能力——struct 和 enum 如何帮你用类型来表达程序的逻辑。
