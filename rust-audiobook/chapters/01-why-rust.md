# 第一章 为什么是 Rust

我们从一个 bug 开始。

这是一段 C 语言代码。创建一个字符串，把它交给另一个指针，然后释放原来的内存。接下来，你通过第二个指针去读取那块内存。程序不会报错，不会崩溃——它会安静地返回一段垃圾数据，或者更糟，返回一段看起来像是正确的数据。

```c
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

int main() {
    char *s1 = malloc(6);
    strcpy(s1, "hello");
    char *s2 = s1;
    free(s1);
    printf("%s\n", s2); // use-after-free: s2 指向已释放的内存
    return 0;
}
```

这就是 use-after-free，C 和 C++ 世界里最臭名昭著的 bug 之一。它不会在测试里被抓到，因为被释放的内存可能暂时还没有被覆盖，程序看起来一切正常。直到某天，一个用户在生产环境触发了这个路径，数据被悄悄损坏了，或者更严重——攻击者利用这个漏洞执行了任意代码。

这一章我们讲三件事：第一，像 use-after-free 这样的内存安全问题到底有多普遍，后果有多严重。第二，现有的解决方案——垃圾回收和手动管理——各自要付出什么代价。第三，Rust 找到了一条什么样的第三条路。

## 内存安全问题有多严重

use-after-free 并不是一个罕见的 bug。微软曾经公开过一个数据：他们每年修复的安全漏洞里，大约七成都是内存安全问题。谷歌的 Chrome 浏览器也有类似的数据，内存安全 bug 占了高危漏洞的大多数。

这类 bug 不只有 use-after-free。常见的还有几种。

第一种是悬垂指针。一个指针指向的内存已经被释放了，但指针还在被使用。刚才那个 C 的例子就是。

第二种是双重释放。同一块内存被释放了两次。这会破坏内存管理器的内部数据结构，后果不可预测。

第三种是缓冲区溢出。往一块内存里写入超过它容量的数据，覆盖掉旁边的内存。这是许多远程代码执行漏洞的根源。

第四种是数据竞争。两个线程同时读写同一块内存，没有加锁。结果是不确定的——可能偶尔正确，可能偶尔崩溃，可能产生一个极其难以复现的 bug。

这些问题有一个共同点：编译器不管，运行时不报错，程序员靠肉眼和经验去避免。这在小程序里也许还能应付，但在几百万行代码的大型项目里，几乎不可能完全避免。

## 两种传统方案：各有代价

面对内存安全问题，业界有两条传统的路。

第一条路是手动管理内存。C 和 C++ 走的就是这条路。程序员自己分配内存，自己释放内存。好处是性能极高，完全没有运行时开销。坏处是一切安全都取决于程序员有没有犯错。几十年的工程经验证明：人会犯错，而且犯了不容易发现。

第二条路是垃圾回收，英文叫 garbage collection，简称 GC。Java、Python、Go、JavaScript 都走这条路。程序员不需要手动释放内存，运行时系统会自动追踪哪些内存还在被使用，定期把没人用的内存回收掉。

GC 确实解决了大部分内存安全问题。你不会遇到 use-after-free，因为 GC 不会释放还在被引用的内存。你不会遇到双重释放，因为释放这件事根本不由你控制。

但 GC 有它自己的代价。首先是性能开销。GC 需要在运行时追踪对象之间的引用关系，需要暂停程序来做垃圾回收。这个暂停有时候只有几毫秒，有时候会更长。对于大多数应用来说，这没什么问题。但对于需要稳定低延迟的场景——操作系统内核、数据库引擎、游戏引擎、嵌入式系统——GC 的暂停是不可接受的。

其次是内存占用。GC 管理的程序通常需要更多内存，因为垃圾不会立刻被回收，而是等到 GC 觉得该清理了才清理。

最后，GC 也没有解决数据竞争问题。Java 有 GC，但 Java 的多线程程序依然会遇到数据竞争。GC 管的是内存什么时候释放，不管两个线程能不能同时修改同一个变量。

所以，两条路各有取舍。手动管理：快，但不安全。垃圾回收：安全，但有运行时开销，而且没解决数据竞争。

## Rust 的第三条路

Rust 选了一条不同的路：在编译期检查内存安全。

Rust 的核心思想叫所有权，英文叫 ownership。每一个值在任何时刻只有一个拥有者。当拥有者离开作用域，值的内存自动被释放。不需要手动 free，也不需要垃圾回收器。编译器在编译的时候就检查好了一切。

我们来看看同样的逻辑在 Rust 里会发生什么。创建一个 String，把它赋值给另一个变量，然后试图使用原来的变量。

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
    println!("{s1}"); // 编译错误：value used after move
}
```

编译器直接拒绝了这段代码。错误信息说：value used after move。意思是：s1 的值已经被 move 到 s2 了，s1 不再有效，你不能用它。

注意，这不是运行时错误，不是异常，不是崩溃。这是编译错误。程序根本不会生成可执行文件。这个 bug 在你写代码的时候就被消灭了，而不是在用户的机器上被发现。

这就是 Rust 和 C 的根本区别。C 允许你写出 use-after-free，然后在运行时默默产生未定义行为。Rust 在编译期就阻止了这种情况的发生。代价是什么？你需要学习所有权的规则，有时候需要换一种方式组织代码。但换来的是：如果程序编译通过了，这类 bug 就不存在。

而且 Rust 的检查是零运行时开销的。所有权的规则只存在于编译器里。一旦编译通过，生成的机器码和手写的 C 代码一样快，没有 GC，没有引用计数，没有任何额外的运行时机制。这就是 Rust 社区常说的零成本抽象——安全性不以性能为代价。

## Rust 的设计哲学

让我们退后一步，看看更大的图景。

Rust 的设计哲学可以用一句话概括：如果编译通过，这类 bug 就不存在。这里的"这类 bug"包括 use-after-free、悬垂指针、双重释放、缓冲区溢出、数据竞争。这些在 C 和 C++ 里需要靠代码审查、静态分析工具、地址消毒器来发现的 bug，在 Rust 里由编译器在编译期直接拦截。

Rust 的编译器以严格闻名。初学 Rust 的时候，你会发现很多在其他语言里可以随手写的代码，Rust 编译器就是不让你过。这会让人沮丧。但换一个角度想：编译器拒绝你的代码，是因为它发现了一个潜在的 bug。编译器是你的合作者，不是你的敌人。它在帮你抓出那些在运行时才会爆发的问题。

Rust 也不是银弹。它不能阻止逻辑错误——你写了一个排序算法但排错了方向，编译器不会管。它不能阻止死锁——两个线程互相等待对方释放锁。它也有一个叫 unsafe 的后门，允许你绕过编译器的检查，但使用 unsafe 需要程序员自己保证安全。Rust 的哲学是：把 unsafe 限制在尽可能小的范围里，让绝大多数代码都在编译器的保护之下。

## 谁在用 Rust

Rust 不是一个实验性语言。它从 2015 年发布 1.0 以来，已经被广泛用于生产环境。

Firefox 浏览器的核心组件用 Rust 重写了。Linux 内核从 6.1 版本开始支持用 Rust 编写驱动。安卓操作系统的蓝牙和 WiFi 模块用了 Rust。亚马逊、微软、谷歌、Cloudflare 都在关键基础设施中使用 Rust。Discord 把一个 Go 写的服务用 Rust 重写之后，消除了 GC 暂停带来的延迟尖刺。

Rust 连续多年在 Stack Overflow 的开发者调查中被评为"最受喜爱的编程语言"。这不是因为它简单——它可能是主流语言里学习曲线最陡的。但一旦你理解了所有权模型，你会发现编译器让你对自己的代码有一种前所未有的信心。

## 回顾

我们来回顾这一章的要点。

第一，内存安全问题——use-after-free、悬垂指针、双重释放、数据竞争——是 C 和 C++ 世界里最常见也最危险的一类 bug。它们不会被编译器发现，也不一定在测试中复现。

第二，传统的解决方案有两条路。手动管理内存性能高但不安全。垃圾回收安全但有运行时开销，而且没有解决数据竞争。

第三，Rust 走了第三条路：用所有权系统在编译期检查内存安全，零运行时开销。如果代码编译通过，这些内存安全 bug 就不会存在。代价是你需要学习并遵守所有权的规则。
